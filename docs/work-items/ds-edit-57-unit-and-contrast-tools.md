# DS-EDIT-57 — Conversion d’unités et correction du contraste

2 novembre 2026 — application, base 16789fb. Réalisation explicitement lancée après validation de la proposition. Procédures applicatives implement-feature, normalize-design-system et revues design/technique/sécurité séquentielles, même agent non indépendant. Sol · Élevée recommandé : protocole de mesure, conversions, moteur de couleur et brouillon raccordés ; aucun sous-agent.

Objectif : conserver le rendu courant au changement d’unité, et proposer au clic d’un badge non conforme une couleur proche atteignant le seuil exact dans le contexte mesuré. Moteurs déterministes sans IA, ni sauvegarde implicite. Modifier la couleur sélectionnée ; sinon choisir texte ou fond. Garder les portées existantes et l’enregistrement explicite.

Périmètre initial : UI px/rem et couleurs hexadécimales opaques déjà éditables ; moteur générique pour conversions fixes et contextuelles (polices, viewport, conteneur, pourcentage et interligne lorsque références qualifiées fournies). Les autres formats restent non éditables selon DS-EDIT-53. Pas de conversion globale d’un token partagé sans preuve de références communes : le changement prépare un geste local selon la portée déjà choisie. Un réglage relatif converti en absolu préserve le contexte actuel, pas tous les futurs viewports/préférences. Mesures de l’iframe et cohérence génération/render/sequence obligatoires, jamais un rem supposé à 16px.

Couleur : varier la clarté Oklab/OKLCH, conserver la teinte et réduire la chroma uniquement pour rester dans sRGB. Recherche bornée et déterministe, classement par écart Oklab après quantification hex ; validation WCAG sur la valeur finale contre toutes les surfaces mesurées. Pas de promesse de minimum mathématique global. Inconnu ou impossible : message explicite, pas de fausse réussite. Une correction dans le contexte courant ne valide pas tous les consommateurs d’un style partagé ; prévenir et conserver la revue de portée.

Critères : rem 1→px16 seulement avec référence16 et→px20 avec référence20 ; aller-retour sans dérive de quantification ; contexte absent refusé, unité incompatible refusée, root font-size correctement contextualisé. Badge AA/AAA prépare le bon seuil selon taille/graisse, couleur originale déjà conforme inchangée, candidat hex final réellement conforme, erreur sans mutation si impossible, choix texte/fond pour autre propriété. Parcours dev/statique/persistance sur copies isolées ; recette humaine préservée avant actualisation.

Références : https://www.w3.org/TR/css-values-4/ ; https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html ; https://www.w3.org/WAI/WCAG22/Understanding/contrast-enhanced.html ; https://bottosson.github.io/posts/oklab/ (matrices publiques de l’auteur, calcul sRGB/Oklab). Aucun parser ni nouvelle dépendance globale. Préexistants et modèles de suivi app inchangés. Statut initial En cours, résultats complétés après contrôles. Doc updated.

## Résultat qualifié

En revue — qualification technique du raccordement courant acquise, acceptation humaine différée. Le commit porteur de cette fiche identifie le candidat, depuis la base ci-dessus. [Décision 026](../decisions/026-contextual-unit-and-contrast-tools.md), [guide courant](../design-system/editor-preview.md#outils-contextuels--ds-edit-5657). Les formats futurs restent des capacités de calcul conditionnelles, pas de nouveaux champs éditables. Référence absente, contexte périmé, dimensions incompatibles et contraste impossible sont explicitement traités sans valeur inventée. Conversion partagée verrouillée en l’absence de références communes qualifiées.

Contrôles exécutés avec Node 24.22.0 et npm 11.8.0 déjà présents localement :

- `npm test` : 143 tests réussis, 20 fichiers. Deux nouveaux tests du moteur couvrent unités, références, compatibilité, ratios AA/AAA, sérialisation, idempotence des couleurs conformes et impossibilité. Un test de session vérifie le verrou de partage d’une conversion contextuelle. Retest ciblé final : 24 tests réussis.
- `npm run test:design-system` : 80 tests réussis ; `npm run test:design-system:docs` : cinq réussis. Sources et dérivés de valeurs conservés.
- HTTP : huit cas réussis en loopback autorisé. Store ciblé : trois réussis (save réel, deuxième propriétaire et dépendance changée refusée), sans répéter toute la campagne d’interruptions non modifiée.
- Développement : quatre cas initiaux de placement/badges conformes ; quatre nouveaux parcours 16px/20px, round-trip, impossibilité et choix texte/fond conformes ; deux retests complémentaires du contour conformes. Desktop/mobile Chromium.
- Statique final : huit parcours conformes, dont espace 16px, géométrie du message, couleurs de badges, conversion réelle, AAA impossible sur texte seul puis fond corrigé, référence racine 20px, choix fond depuis géométrie et routage du contour avec seuil non textuel.
- Persistance : deux parcours desktop/mobile réussis dans une copie isolée ; unités et couleurs retrouvées après rechargement, puis relecture des sources sauvegardées et application compilée réussies.
- Typecheck et build conformes sur copie des seuls fichiers livrables (préexistant non suivi SemanticStyles.tsx incompatible préservé dans le checkout). ESLint et Prettier ciblés conformes ; diff et sélection examinés. Journaux locaux ignorés `tools-*.log` dans `.local/ds-edit-53/` du lab.

Échecs initiaux conservés dans les journaux : une attente de test exigeait AAA en modifiant le blanc du texte sur un bleu dont le contraste maximum était insuffisant ; le test vérifie maintenant le refus puis la correction du fond. Une répétition mobile tentait d’enregistrer une couleur identique à la correction déjà enregistrée sur desktop ; les couleurs de départ des deux formats sont désormais distinctes. Aucun faux succès ni assouplissement des seuils pour faire passer ces cas.

Revues successives, même agent non indépendant : Design Reviewer satisfaisant sur les contextes testés (gestes, erreurs, portées, message sans sauvegarde implicite) ; Technical Reviewer satisfaisant (API pure, mesures typées, contextes frais, calcul borné, quantification revalidée et persistance) ; Security Reviewer satisfaisant dans le périmètre local (aucun accès/URL/fournisseur nouveau, chaînes couleur fermées, cardinalités bornées, nombres finis et opérations serveur habituelles). Pas d’audit global ni de certification d’accessibilité. Les mesures de toutes les unités relatives futures et tous les consommateurs distants ne sont pas qualifiées ; la recherche couleur est une approximation bornée, explicitement documentée.

Doc updated : fiche, décision, spécification, guide et suivi de fabrication racine. Préexistants, modèles app/J4/J5 et publication inchangés. Reprise : recette humaine des outils, extensions de formats et nomenclature dans leurs mandats explicites.
