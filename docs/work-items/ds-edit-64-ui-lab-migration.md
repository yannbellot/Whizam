## Résultat attendu et limites

Le designer ouvre UI Lab, choisit un composant et un exemple préparés, examine variantes/parties/propriétés/états, règle son apparence et ses portées, puis enregistre. Le parcours complet fonctionne **avec Storybook arrêté**. Les composants React, autorités YAML, identités et règles d’attribution restent communs à l’application et à Storybook. Le développeur reçoit les sources, exemples, propriétés, règles d’usage et tests dans un Storybook de documentation sans dépendance à l’éditeur actif.

La migration porte sur les capacités actuellement livrées, y compris navigation vers les usages et retour au réglage, actualisation/conflits, outils d’unité/contraste et assistance Codex optionnelle. Elle ne rétablit pas les anciennes fonctions supprimées : comparaison DS-EDIT-62, éditeur Styles et création manuelle des anciens catalogues. Le code suivi et les contrats les plus récents doivent être rapprochés des sections historiques des guides avant réalisation. Les catalogues restent consultables.

Exclusions : nouvelle bibliothèque UI, backend distinct, édition de code/CSS libre, construction de pages, nouveau composant ou domaine éditable, changement de valeur/direction visuelle du produit, collaboration distante, migration des données métier, publication et clôture des acceptations humaines J4/J5. L’édition reste un outillage local de développement ; le runtime compilé et les distributions de consultation ne doivent pas acquérir un service d’écriture ou une connexion IA.

## Architecture proposée et alternatives

Choix minimal proposé : conserver React Router/React/TypeScript/Vite et les CSS Modules. Sous `/ui-lab`, une coque d’atelier client et un aperçu isolé consomment les vrais composants et fixtures partagées. L’aperçu ne charge aucune API Storybook. Un transport borné et validé porte le contexte de scène et l’accusé d’application ; il ne transporte ni CSS libre, ni chemin, ni capacité du writer. L’iframe est une option d’isolation proposée, à confirmer en A ; ses routes exactes et la disposition restent provisoires.

Répartition proposée, chemins indicatifs à confirmer en A :

- `src/design-system/editor/` : contrats, règles et contrôleurs sans dépendance à un hôte ; séparer modules purs et modules navigateur.
- `src/ui-lab/editor/` : navigation, commandes, sélection et adaptateur d’aperçu ; fixtures partagées près de leurs composants ou compositions.
- `scripts/design-editor/` : service local, persistance, observation et assistance serveur, sans import Storybook ; plugin Vite de développement comme raccordement, sans backend supplémentaire.
- `.storybook/` : stories, Docs, contrôles de démonstration et tests de composants, puis aucun writer ni panneau DS-EDIT après F.

Le moteur déterministe et les composants partagés restent les mêmes pour tous les consommateurs. Storybook montre la génération enregistrée ; le brouillon UI Lab reste isolé jusqu’à Enregistrer. Storybook conserve ses outils standards de démonstration, distincts des réglages persistants du design system.

Alternatives écartées à ce stade : déplacement global en une fois (cumule les changements de contrats et complique le diagnostic) ; deuxième éditeur construit par copie (règles divergentes) ; UI Lab embarquant l’iframe Storybook (autonomie fictive). L’extraction progressive avec adaptateur temporaire permet des comparaisons sans promettre deux éditeurs durables.

Critères d’autonomie supplémentaires :

1. Un lancement dédié à l’atelier ne charge ni CLI, manager, canal ou index Storybook ; aucun import transitif `storybook/*`, `@storybook/*` ou fichier d’exécution sous `.storybook` dans son graphe. Les devDependencies Storybook restent installables pour sa documentation : l’indépendance ne signifie pas leur retrait du kit.
2. Le snapshot et la révision nécessaires à Enregistrer sont produits et accessibles sans construire Storybook. Les références `.storybook` conservées dans un manifeste sont justifiées comme consommateurs documentaires, pas comme services ou bootstrap requis pour l’éditeur.
3. Réglages locaux, partagés et rétablissement conservent les identités/attributions ; aucun élargissement de matrice et aucun changement de valeur produit causé par la migration.
4. État d’une scène, génération, session et accusés périmés sont vérifiés. Hover/focus présentés visuellement restent distingués d’une interaction réelle ; mesures inconnues restent non mesurées.
5. UI Lab ordinaire et builds compilés ne fournissent ni capacité ni endpoint actif d’écriture/assistance. Tester des refus HTTP réels, pas seulement l’absence du bouton.
6. Un changement externe/rechargement HMR ne détruit pas silencieusement le brouillon ; une issue de sauvegarde inconnue se résout par statut, sans nouvel identifiant automatique.
