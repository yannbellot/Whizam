# Consommation des tokens UI

**DS-ARCH-01 :** valeurs et références dans le JSON DTCG canonique ; règles et recettes dans leurs contrats YAML. Les recettes contextuelles décomposent les quantités en paramètres typés, gardent une syntaxe CSS fermée et leurs consommateurs. Elles ne sont pas des tokens opaques ou une exception autorisant des valeurs visuelles libres. Voir le [contrat courant](../../src/design-system/authority/README.md) et [027](../decisions/027-dtcg-authority-and-css-recipes.md).


Règle validée le 2 novembre 2026, [décision 024](../decisions/024-tokenized-ui-composition.md).

Toute valeur visuelle du produit est consommée par un token sémantique ou de composant. Les consommateurs ne référencent pas directement une primitive. Les tokens peuvent atteindre une primitive directement ou via un rôle sémantique. L’interface de l’éditeur Storybook reste exclue. Les mots-clés de structure/reset (display, position, auto, zéro de remise à zéro, dimensions relatives structurelles) ne sont pas des échelles visuelles à tokeniser.

Pour chaque nouvel usage, l’IA identifie propriétaire, partie, état et fonction ; elle cherche un token de même sens et compatible. Une même valeur ne suffit pas à créer une intention commune. Un rôle transversal documenté utilise un token sémantique ; un réglage local utilise un token de composant. Les fiches de la matrice V1 restent propriétaires des réglages éditables. Les propriétés de composition hors matrice (ombre, transition, taille fluide, identité typographique du UI Lab) sont déclarées dans ui-composition.yaml avec référence, justification, fichier, sélecteur et propriété. Leurs identifiants sont stables et ne sont pas régénérés à partir de l’ordre des règles.

La migration DS-EDIT-52 prépare 98 tokens complémentaires, 49 primitives CSS de composition, ainsi qu’un token de composant d’échantillon par primitive couleur (9 dans le socle canonique), réutilise les primitives canoniques quand les valeurs exactes correspondent et les rôles de texte principal/secondaire pour huit usages. Elle remplace les anciens alias géométriques consommés par les pages de projet, conserve 188 réglages V1 et les alias de compatibilité nécessaires aux catalogues. Aucun style de l’éditeur n’est migré. Les tokens de composition ne sont pas exposés comme réglages V1 éditables dans Storybook ; leur autorité reste le YAML.

`npm run tokens:generate` publie les dérivés, sans éditer ceux-ci à la main. `npm run validate:design-system` contrôle aussi la composition. Le contrôle couvre les déclarations CSS visuelles src/app, les références directes aux primitives et les consommateurs déclarés. La géométrie des nuanciers est mutualisée dans des tokens de composant. Leurs couleurs utilisent les variables des tokens représentés ; les échantillons de primitives passent par des alias de composant dérivés de la règle primitiveColorSamples. Aucun réglage visuel de ces catalogues ne consomme directement une primitive. Les valeurs inline de démonstration des catalogues proviennent des tokens ; les nouveaux styles inline doivent suivre la même règle et être examinés en revue. Le contrôle automatique ne constitue pas un analyseur exhaustif de toute expression JavaScript/CSS future.

La portée partagée conserve ses protections : absence d’attribution → « Aucun token partagé d’origine n’existe. » ; inventaire incomplet → « Inventaire incomplet : modification partagée indisponible. » ; valeur hors domaine compatible → « Cette valeur est incompatible avec un usage lié. » Une autre erreur de préparation ne se présente plus comme une incompatibilité de valeur. L’inventaire reste actuellement global : une anomalie peut bloquer toutes les modifications partagées.

Le manifeste v10 ajoute l’autorité aux lectures observées et aux révisions ; le writer la conserve pendant un réglage V1. Les journaux/reçus d’une version antérieure ne sont pas convertis ni supprimés. La recette migrée utilise une nouvelle racine avec les seuls YAML de valeurs de l’ancienne instance ; comptes et anciens reçus restent dans leur instance d’origine.
