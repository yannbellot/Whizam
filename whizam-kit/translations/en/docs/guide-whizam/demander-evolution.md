# Requesting a change

To evolve an existing project, describe the affected area, observed problem, expected result and what must be preserved. A new conversation or feature does not require reinitialization.

## Two example requests

> Local correction: “On Contact, the confirmation message is hard to notice. Prepare a hierarchy improvement while preserving the form and other pages.”

> New journey: “I want visitors to edit their request before confirmation. Analyze the screens, states and data involved and propose a verifiable slice of work.”

Scope depends on actual effects. A shared change can affect several pages; the assistant must explain the extent before implementation.

## Reuse components

Ask the assistant to examine available components and variants before adding new ones. Appearance differences in shared components must be explicit and documented. You review the result in the application and Storybook; token and generation details remain the assistant’s responsibility within the agreed mandate.

> “Reuse existing components where appropriate. Identify variants or states to add and affected pages.”

## Review the result

You should find the authorized changes, relevant states and remaining limits. Also check elements to preserve. If the proposed scope changes materially, ask for a revised proposal before deciding.
